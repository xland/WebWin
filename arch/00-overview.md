# WebWin 项目概述

## 一句话定位

WebWin 是一个**用 C++ 开发、基于 WebView2 的 Windows 桌面 GUI 开发框架**，
功能定位对标 **Tauri**：用 Web 前端技术（HTML / CSS / JS）写界面，
用原生语言写逻辑，二者通过桥接层通信。

## 核心特征

| 维度 | 内容 |
| --- | --- |
| 实现语言 | C++（当前标准 C++20） |
| 渲染内核 | Microsoft Edge WebView2 |
| 目标平台 | **仅 Windows**，不做跨平台兼容 |
| 对标产品 | Tauri |
| 程序形态 | Windows GUI 子系统（`SubSystem=Windows`），非控制台 |

## 设计原则（最高优先级）

1. **效率尽可能高。**
2. **体积尽可能小。**
3. **常驻内存尽可能少。**

> **冲突裁决规则**：任何设计若与"高效率 / 小体积 / 少常驻内存"相冲突，
> **不自行取舍，一律提交给项目负责人抉择。**
> 记录时应同时列出冲突点、两种方案各自的效率、体积与常驻内存代价，
> 由负责人拍板后再继续实现。

### "体积"的口径（重要）

**体积指的是最终分发给用户的文件体积，不是 SDK 的体积。**

| | 组成 | 说明 |
| --- | --- | --- |
| **SDK** | `exe` + `.d.ts` | 给开发者用。SDK 内包含 `.d.ts`，不受体积约束 |
| **最终分发物** | `exe` + 开发者自写的 HTML / CSS / JS | 给用户用。`.d.ts` **不会**随分发物交付 |

因此：任何只增加 SDK 体积、但不进入最终分发物的东西（如 `.d.ts`、调试符号、
开发期辅助文件），**不构成与"小体积"原则的冲突**，无需上报抉择。
反之，凡是会进入最终分发物（核心就是 `exe`）的体积开销，一律按上面的裁决规则处理。

推论（已体现在现有配置中）：不引入重型第三方依赖，
倾向静态链接、避免额外运行时（当前运行库即为 `MultiThreaded` / `MultiThreadedDebug`）。

### "常驻内存"的口径（重要）

**前两条是一次性开销，这一条是持续整个进程生命周期的开销。**

| 原则 | 开销形态 |
| --- | --- |
| 体积小 | 交付那一刻定下来，之后不再增长 |
| 效率高 | 花掉就过去了 |
| 常驻内存少 | **进程活着就要占着**，且会随着"多留一处"逐处累积 |

它也是最隐蔽的一条：多余的状态不会报错、不会明显变慢、profiler 里
也不扎眼，只是每个用本框架做出来的应用都悄悄多占一份。叠加本项目定位后
影响更实 —— WebWin 是**框架**，这里每留一分状态，下游每个应用的每个进程都要付。

**典型反面例子（本项目已踩过并修正）**：`package.json` 的 `window` 段落
被解析成 `JsonObject` 后存进文件作用域的静态，只为在紧接着的下一个函数里
读一次。结果那棵 JSON 树、它里面的每个字符串、以及它依赖的 WinRT 对象，
全部活到进程退出。修正后 `readPackageJson()` 把它**返回**、`init()` 直接
传给 `Win::Create(...)`，用完析构，一滴不剩。

> 判据一句话：**用完还不放手的、又说不出为什么还留着的，就是泄漏。**

**允许留下的四条理由**（必须能对上其中一条，否则不许沉淀成状态）：

| 理由 | 本项目实例 |
| --- | --- |
| 多处要读，且读取时机不确定 | `packageBaseDir` —— 每次加载页面解析入口 HTML 要用，`getAppPath` 也要用 |
| 必须活过创造它的那次调用 | `dispatcherCtrl` —— 必须活过所有 `TryEnqueue` 排进去的任务（见 `App::runLater`） |
| 它是某类资源的唯一发号器 | `Win::lastId` —— 窗口 id 自增的当前值 |
| 留着是为了能被提前撤销 | `Dialog::pending` —— 配合 `removeByPage` 清掉尚未执行、页面已销毁的请求 |

**反过来：只被读一次的，用参数传，不要落字段或静态。**

```cpp
// 不好：只为在下一个函数里读一次，却让整棵 JSON 树陪着进程走到最后
static JsonObject windowConfig;          // 或 App 成员，一样糟糕
void App::readPackageJson() { ...; windowConfig = Json::getObject(webwin, L"window"); }
void App::createWindow()    { Win::Create(windowConfig); }

// 好：读完就交出去，谁来用谁持有，用完即析构
JsonObject App::readPackageJson() { ...; return Json::getObject(webwin, L"window"); }
// init() 里：不再暂存，直接接着往下传
auto windowConfig = app->readPackageJson();
Win::Create(windowConfig);
```

**写代码时逐条自问：**

1. 新加的字段 / 静态，**有几处会读它？** 只有一处 → 改成参数。
2. 它**什么时候被销毁？** 答案是"从不"或"进程退出时" → 它是泄漏。
3. 它是**真被共享，还是只是中转？** 中转 → 干掉中间层。
4. 里面若存指针 / 句柄，**有没有配清理钩子**（窗口没了要能摘，
   形态见 `Win::winProc` 的 `WM_DESTROY` 里 `Menu::removeByPage` /
   `Dialog::removeByPage`）。

## 设计取向

- **只支持 Windows 是明确的产品决策，不是阶段性妥协。**
  所有设计（窗口管理、消息循环、系统集成、打包分发）都可以直接绑定 Win32 / WebView2 API，
  不需要为跨平台抽象付出代价，也不需要维护条件编译分支。
- 前端承担界面表现，C++ 承担系统能力与业务逻辑。
- 目标是做成"框架/库"形态，而非单个应用：使用者在此之上开发自己的桌面程序。

## 非目标（明确不做）

- 跨平台支持（Linux / macOS 不在范围内）
- 浏览器内核可替换（不使用 CEF、Electron、系统 WebView 以外的内核）
- 移动端

## 与 Tauri 的对照（用于澄清定位）

| 能力 | Tauri | WebWin |
| --- | --- | --- |
| 宿主语言 | Rust | C++ |
| 渲染内核 | 各平台系统 WebView（Windows 上即 WebView2） | WebView2 |
| 跨平台 | 是 | 否（仅 Windows） |
| 前端 ↔ 原生通信 | 命令 + 事件通道 | 待设计 |
