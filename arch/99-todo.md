## T001 详情：JSON 序列化开销实测

- **背景**：框架用 `winrt/Windows.Data.Json.h` 做 JSON 序列化/反序列化，不引外部库。
  WinRT 对象模型经 COM ABI，取值/构造带引用计数与跨 ABI 开销，通常高于纯头文件解析库。
- **风险点**：消息通道是**每次 API 调用必经路径**，该开销会直接叠加到调用延迟上。
- **做法**：通信层成型后，对典型消息体做一次序列化/反序列化开销实测。
- **处置规则**：若确认成为瓶颈，**不自行替换方案**，按 `00-overview.md`
  的冲突裁决规则上报负责人抉择。

## T004 详情：批量命令能力

- **目标**：开发者的 JS 能一次发起多条命令，减少 JS ↔ C++ 的 IPC 往返次数。
- **候选形态**：`invoke_batch()`，或自定义批量接口（最终形态待设计）。
- **动机**：项目以"效率尽可能高"为最高原则之一，单次调用一次往返在高频场景下开销明显。
- **关联**：与 **T001**（JSON 开销实测）同属通信层性能议题，建议在通信层一并考虑。
- **待明确**：批量调用的响应是整体返回还是按子项分别返回；子项失败如何处理；
  批量内部是否保证执行顺序。
